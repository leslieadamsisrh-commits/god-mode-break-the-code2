# PRODUCTION RULES

## Rule 1 — One production objective at a time
The Studio Director may capture unlimited ideas, but only one primary production gate is active unless a second task is explicitly declared non-interfering.

## Rule 2 — Protect the playable build
Never rewrite or refactor working systems merely to make them cleaner while another gate is being tested.

## Rule 3 — Separate departments
Combat, Animation/Sprites, Level Design, Multiplayer/Engineering, Story/Lore, UI/VFX/Audio, QA, and Business/Release each own their domain. Cross-department changes require Studio Director review.

## Rule 4 — Approval has meaning
When a visual/mechanic is explicitly approved or locked, preserve it until a later decision explicitly supersedes it.

## Rule 5 — Historical chat is reference, not authority
Old chat instructions may contain excellent ideas and recovery information, but they do not outrank current code or current locked decisions.

## Rule 6 — Regression before expansion
A new feature is not complete until protected systems still work.

## Rule 7 — Build small, verify, checkpoint
Prefer isolated passes and small reversible changes over large all-at-once rebuilds.

## Rule 8 — Playtest language is first-class data
Natural comments such as "this feels perfect," "this is firing from her chest," or "camera is too bouncy" must be translated into approvals, bugs, tuning notes, or parked ideas.

## Rule 9 — Never destroy recovery paths
Do not delete old approved branches, assets, or recovery checkpoints merely because a newer direction exists.

## Rule 10 — Ship the game
The production hierarchy is:
FUN → STABILITY → MULTIPLAYER → VISUAL POLISH → CONTENT.
